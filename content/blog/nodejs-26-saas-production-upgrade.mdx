*Updated November 1, 2026: Node.js 26 is now Active LTS. This guide was first published in July, when 26 was still the Current line and the advice was "test now, wait for LTS". That wait is over.*

Node.js 26 became a Long Term Support release on October 28, 2026. The [Node.js 26.13.0 release notes](https://nodejs.org/en/blog/release/v26.13.0) mark the transition under the codename "Lithium" and say the line will receive updates through the end of April 2029.

For SaaS teams, that changes the question. It is no longer "should we try the new runtime?" but "when do we move production, and how do we do it without an incident?"

Runtime upgrades sit below almost everything: builds, API routes, background jobs, database clients, image processing, auth libraries, observability agents and deployment tooling. A small incompatibility affects the whole release, not one feature. This guide covers what changed, who should move first, a step-by-step Node.js 26 LTS upgrade plan, how to test it, what commonly breaks, and how to roll back.

---

## What Changed With the LTS Promotion

The LTS release itself contains no new behavior. According to the release notes, 26.13.0 only updates metadata such as `process.release` compared with 26.12.1. Everything that can break your application arrived earlier, in 26.0.0 and the 26.x releases that followed.

What the promotion does change is the support picture. The [Node.js Release Working Group schedule](https://github.com/nodejs/Release) now lists:

| Line | Status (November 2026) | End of life |
| --- | --- | --- |
| Node.js 26 "Lithium" | Active LTS since October 28, 2026 | April 30, 2029 |
| Node.js 24 "Krypton" | Maintenance LTS since October 20, 2026 | April 30, 2028 |
| Node.js 22 "Jod" | Maintenance LTS | April 30, 2027 |

Two practical consequences follow:

- **Teams on Node.js 22** have six months of support left. They should plan to move this quarter, and going straight to 26 avoids doing the work twice.
- **Teams on Node.js 24** are not in a hurry. Maintenance LTS still gets critical and security fixes, but new improvements now land on 26. A planned move in the next few months is reasonable.

The schedule also changes from Node.js 27 onward. The project has started a 27.x Alpha line, and from 27 every major version will become LTS, with one release a year. Node.js 26 is the last line under the old odd/even model, so the habit of skipping odd numbers will stop applying.

## What Node.js 26 Changes for a SaaS Application

The [Node.js 26.0.0 release notes](https://nodejs.org/en/blog/release/v26.0.0) list the breaking changes. These are the ones most likely to matter in a SaaS codebase.

### Native addons must be rebuilt

Node.js 26 uses `NODE_MODULE_VERSION` 147 and V8 14.6. Packages built on Node-API usually keep working across versions. Packages tied to a specific module ABI need a new prebuilt binary or a rebuild. Higher-risk areas include:

- database drivers with native components;
- image, video, canvas and PDF tooling;
- password hashing libraries;
- observability and APM agents.

Do not infer compatibility from `npm install` succeeding on one laptop. Test the same operating system, CPU architecture, package manager and container base image used in production.

### Linux images may need libatomic

The 26.13.0 release notes warn teams coming from Node.js 24, 22 or older that the official Linux binaries have been linked against `libatomic` since Node.js 25. Depending on your distribution, it may have to be installed separately. A minimal Docker image can build fine and then fail when `node` starts. Add the package to your runtime stage if your distribution needs it, and test the real image.

### Removed and deprecated APIs

Node.js 26 removes:

- `http` `writeHeader()`, replaced by `writeHead()`;
- the private legacy stream modules (`_stream_readable`, `_stream_writable`, `_stream_duplex`, `_stream_transform`, `_stream_passthrough`, `_stream_wrap`), replaced by `node:stream`;
- the `--experimental-transform-types` flag.

It also runtime-deprecates `module.register()`, which some loaders and instrumentation tools use. The [Node.js deprecations reference](https://nodejs.org/api/deprecations.html) lists replacements.

Your own code may not call any of these. A dependency, test runner, loader or APM agent might. Run your suite once with:

```bash
NODE_PENDING_DEPRECATION=1 node --trace-deprecation ./server.js
```

The stack traces show which package owns each call site.

### Undici 8 under `fetch`

Built-in `fetch` now uses Undici 8. Test the failure paths of your real integrations, not just a happy-path request: aborted requests, redirects, proxies, timeouts, streaming responses, large uploads and third-party APIs that return unusual headers.

### Temporal is on by default

The Temporal date API is available without a flag. That is useful for billing dates, trials, bookings and time zones, but do not combine a runtime upgrade with a date-library rewrite. Upgrade first; adopt Temporal later as a separate change with its own tests. Also note that code which feature-detects `globalThis.Temporal` will now take a different branch on the server than in older browsers.

### Smaller behavior changes worth a test

The 26.0.0 notes also list changes that rarely matter but are hard to debug when they do: `localStorage` returns `undefined` unless `--localstorage-file` is set, and the extensionless CommonJS exception for `"type": "module"` packages has been removed. If you run scripts without file extensions inside an ESM package, test them.

## Which Node.js 26 Patch to Deploy

"Node.js 26" is not a complete security decision. The [October 21, 2026 security release](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases) fixed ten vulnerabilities across the 22, 24 and 26 lines, including four rated high. Among them are an out-of-bounds write in the bundled Brotli decoder and TLS identity checks that could accept unusual IP address spellings. The fixed versions are 26.12.1, 24.22.1 and 22.23.4.

**Update, November 12:** a newer [security release on November 11](https://nodejs.org/en/blog/vulnerability/november-2026-security-releases) fixed 16 more CVEs, mostly in HTTP/2 and TLS. The current patched versions are 26.13.1, 24.22.3 and 22.23.5. See [the November 11 brief](/blog/nodejs-november-2026-security-release-http2-tls) for who is exposed. The Brotli out-of-bounds write from October (CVE-2026-111497) was added to CISA's Known Exploited Vulnerabilities catalog on October 27, so those fixes matter too.

So:

- deploy the newest 26.x patch, and never anything older than 26.13.1;
- if you stay on 24 for now, make sure you run 24.22.3 or later;
- pin the major version, not an early patch, so security updates keep arriving through your normal update process.

## Step-by-Step Node.js 26 LTS Upgrade Plan

The plan separates discovery, compatibility and rollout, with clear exit points if something is not ready.

### 1. Inventory every place Node runs

List the version used by local development, CI, preview deployments, production web servers, serverless functions, queue workers, scheduled jobs, migration scripts, and each Docker build and runtime stage. Record the owner and where the version is set for each.

A Next.js project, for example, may build with one Node version, run API routes on a platform runtime, and run cron jobs from a separate image. Changing `.nvmrc` does not move all of them together.

### 2. Check framework and platform support

Next.js 16 requires Node.js 20.9 or newer according to its [version 16 upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16), so Node.js 26 meets the minimum. A framework's minimum only says which old runtimes are rejected. Also confirm your hosting platform offers Node.js 26 for builds and functions, and that your APM agent supports it.

### 3. Record a baseline

Capture error rate, startup time, memory, CPU, API latency, build time, job throughput and outbound request failures on the current runtime. Without a baseline, a "successful" deploy can hide a regression. If you lack these signals, a [minimum viable observability](/blog/minimum-viable-observability-saas) setup is the first task.

### 4. Run CI on both versions

```yaml
strategy:
  matrix:
    node-version: [24, 26]
```

Run unit and integration tests, the production build, the container build, database migration checks, and smoke tests against real supporting services. Give the dual-version matrix an end date; it is a migration tool, not permanent CI.

### 5. Rebuild from a clean slate

Install from the lockfile with an empty cache, build the real container, and start it. Read native addon build output, engine warnings and deprecation warnings. Fix warnings with an application change or a dependency upgrade, or treat them as a reason to wait. Do not silence them globally.

### 6. Update every version source together

```text
.nvmrc
package.json "engines"
CI setup-node version
Dockerfile build and runtime stages
hosting platform setting
worker and cron images
```

Log `process.version` at startup or expose it in a health check, so you can confirm what is actually running.

### 7. Canary, then roll out in stages

Send a small share of traffic, or one low-risk worker, to Node.js 26. Compare memory, event-loop delay, outbound request errors, restarts and job retries against the baseline. Define rollback thresholds before the deploy. Then widen exposure in steps.

Do not combine the runtime change with a framework major, a database migration, a new base image distribution or a large dependency refresh. Smaller change sets are easier to diagnose and revert.

## How to Test the Upgrade

Most runtime migrations do not fail because nobody ran the tests. They fail because the tests did not represent production. Before approving, exercise:

- a cancelled upload and a forced upstream timeout;
- a worker restarted mid-job;
- a large response through the same proxy used in production;
- graceful shutdown and database pool recovery;
- trace and log correlation across services;
- password hashing, image processing and any other native-addon code path.

The broader [audit checklist for MVPs before real users](/blog/what-to-audit-in-a-vibe-coded-mvp-before-real-users-see-it) is a useful companion for the non-runtime parts of this review.

## What Commonly Breaks

- **The build passes but the container will not start.** Usually a missing system library (such as `libatomic`) or a native binary not yet published for your architecture.
- **The web app works but background jobs do not.** Workers often have their own Dockerfile and load different dependencies. Treat every deployed process as its own migration target.
- **CI and production disagree.** CI tests 26 while production still installs 24, or the reverse. The green check means nothing until the version sources match.
- **An APM or loader package breaks quietly.** Tools that hook module loading are the most likely to hit `module.register()` deprecation warnings or removed internals.
- **An old patch stays pinned.** Locking an early 26.x release forever loses the security fixes that are the point of being on LTS.

## Rollback Plan

Prepare rollback before the first production deploy, not after a bad one:

- keep the last known-good Node.js 24 image or deployment available until 26 has passed the agreed observation window;
- make the runtime a single, reviewable change (one pull request touching the version sources) so reverting it is a revert, not an investigation;
- if you deploy to a platform with instant rollback, confirm the previous deployment is still retained; the [Vercel deployment retention guide](/blog/vercel-deployment-retention-rollback-plan) shows why retention settings matter here;
- write the rollback triggers down: for example, an error rate or memory level above the baseline for a set period. Pick thresholds from your own baseline; any numbers you start with are illustrative until measured.

Rolling back the runtime should not require rolling back data. That is another reason not to bundle schema migrations into the same release.

## Frequently Asked Questions

### Is Node.js 26 ready for production now?

Node.js 26 entered Active LTS with release 26.13.0 on October 28, 2026, so the runtime itself is now a supported production choice. Your application is ready only once your framework, native dependencies, hosting platform and rollback path have been tested on it.

### Do I have to leave Node.js 24 right away?

No. Node.js 24 moved to Maintenance LTS on October 20, 2026 and is scheduled to receive critical fixes until April 30, 2028. Teams on Node.js 22 have less time: its end of life is April 30, 2027.

### Which Node.js 26 version should I deploy?

Use the newest 26.x patch, and nothing older than 26.13.1, which contains the November 11, 2026 security fixes on top of the October 21 ones.

### Should I enable the Permission Model as part of this upgrade?

Not as a side effect. Node's [Permission Model](https://nodejs.org/api/permissions.html) is stable but opt-in through `--permission`. It is worth evaluating for narrow processes such as a document converter or webhook handler, as a separate rollout after the runtime upgrade is stable.

## Upgrade Checklist

- [ ] Every Node runtime (web, workers, cron, scripts, CI, Docker stages) is inventoried.
- [ ] Framework, hosting platform and APM support for Node.js 26 is confirmed.
- [ ] CI runs on 24 and 26, including the production and container builds.
- [ ] Native dependencies work on the production OS and architecture; `libatomic` is present if needed.
- [ ] Deprecation warnings have owners and outcomes.
- [ ] The deployed version is 26.13.1 or newer.
- [ ] Baseline metrics are recorded and the running version is visible in diagnostics.
- [ ] A canary, rollback thresholds and the last known-good artifact are ready.

## Next Step

Teams on Node.js 22 should schedule this upgrade now; teams on 24 can plan it calmly over the next few months. Either way, start with the runtime inventory and a baseline. If that exercise shows unclear deployment ownership, missing metrics or no reliable rollback, those gaps are the real risk, and a focused [production readiness upgrade](/services/production-readiness-upgrade) can turn them into a repeatable release process before the next runtime change.
